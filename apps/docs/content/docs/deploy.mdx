Skiffr deploys as the api, up to four Next apps, and a postgres database. All of them read the same env keys, see [environment](/docs/environment).

## Docker compose

The quickest way is the root `docker-compose.yml`, written for you by `install.sh`, see [install](/docs/install). It runs `db` (`pgvector/pgvector:pg17`), `api`, `dashboard`, `web` and `docs`, pulled from `ghcr.io/findmalek/skiffr-<app>:${SKIFFR_VERSION}`. Everything restarts with `unless-stopped`, waits for its dependency to be healthy (the api waits for the database, the apps wait for the api) and keeps the data in the named volume `db-data`. The compose file holds no secret, all of them are in `.env`.

| Piece | Detail |
| --- | --- |
| ports | site 3000, api 3001, dashboard 3002, docs 3003, all bound to `127.0.0.1` (`SKIFFR_BIND` and `SKIFFR_<APP>_PORT` change that). The database is never published |
| `SKIFFR_VERSION` | the image tag: `latest`, `0.1` (follows the patch releases of 0.1) or an exact `v0.1.2` |
| profile `domain` | adds Caddy on ports 80 and 443 with automatic certificates for `SKIFFR_DOMAIN` and its `dashboard.`, `api.` and `docs.` names. Set by `install.sh --domain` |
| profile `autoupdate` | adds the image updater, see below. Set by `install.sh --autoupdate` |
| profiles are switched in `.env` | `COMPOSE_PROFILES=domain,autoupdate`, then `docker compose up -d` |

`docker-compose.build.yml` is an override that builds the four images from the checkout: `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`. In a clone, `./scripts/setup.sh --build` writes `COMPOSE_FILE` into `.env` so a plain `docker compose up -d --build` does it.

A fresh instance starts empty (`SEED=none`), the demo data is only for development. `ADMIN_EMAIL` and `ADMIN_PASSWORD` create the first admin and reset it to those values on every api start. Behind the bundled Caddy `TRUSTED_PROXY_COUNT` is `1`, on localhost it is `0`, see the client address section below. The api sets secure cookies only when `DASHBOARD_URL` is https, so a plain `http://localhost` setup signs in.

### Updates

Every release publishes new images and a compose file. Three ways to get them, from least to most automatic:

1. **By hand, whenever you like.** `./skiffr update` first dumps the database to `./backups` (it stops if that fails, `--no-backup` skips it), then downloads the compose file of the latest release (checked against its `SHA256SUMS`, which guards against a corrupt download, not a compromised release), pulls the images and recreates the containers that changed. `./skiffr status` tells you whether a newer release exists.
2. **Automatically, every day.** `install.sh --autoupdate` (or `COMPOSE_PROFILES=autoupdate` in `.env`) starts [Watchtower](https://github.com/nicholas-fedor/watchtower), pinned to `1.24.0` (a community maintained fork: the original `containrrr/watchtower` is archived). It checks at 04:00 UTC (`SKIFFR_UPDATE_SCHEDULE`, six field cron), only touches containers labelled `com.centurylinklabs.watchtower.enable=true` (the api, dashboard, web and docs, never the database or itself), cleans old images and restarts one container at a time. It follows the tag in `SKIFFR_VERSION`, so it works with `latest` or `0.1` and does nothing for an exact `vX.Y.Z`.
3. **Pinned.** An exact `SKIFFR_VERSION=v0.1.2` never changes until you change it.

Watchtower needs the docker socket (`/var/run/docker.sock`), and whoever controls that socket is root on the host. That is why it is opt-in and off by default: enable it only on a machine where you accept that, and prefer `./skiffr update` on a shared server. Automatic updates apply the images only. A change to the compose file itself (a new service or variable) needs `./skiffr update`.

Automatic updates take no backup and have no undo: a release with a bad migration reaches you at 04:00 and the database stays migrated. Run `./skiffr backup` on a schedule of your own if the data matters, or stay on `./skiffr update`.

Rules that make updates safe (a convention reviewed in pull requests, nothing enforces it yet):

- migrations run when the api starts and must stay backwards safe: a release adds tables and columns and never drops or renames one in the same release that stops using it. So the previous version still runs on the new schema, and a rollback is just a pin
- compose changes keep old `.env` files working: a new variable always has a default
- the database image is never updated automatically. A new Postgres major version needs a dump and restore: `./skiffr backup`, stop, change the image tag, remove the volume and restore

**Roll back:** set `SKIFFR_VERSION=v0.1.2` in `.env` (or `./skiffr update --version v0.1.2`) and run `docker compose up -d`. The release workflow never moves a `vX.Y.Z` image tag to another build: if one exists it must come from the same commit or the run stops. A bad migration is not undone by a rollback: restore the backup `./skiffr update` took.

**Know when an update exists.** `./skiffr status` always asks GitHub. For the api to know by itself set `UPDATE_CHECK=true`: `GET <api>/version` then also returns `latest` and `updateAvailable`. It is a plain request for the latest release tag every six hours, nothing about you or your server is sent beyond what any HTTP request carries, and it is off by default. `GET /version` always returns the running `version` and `commit`.

**The extension does not update itself.** A folder loaded unpacked is not updated by Chrome. Your server serves the matching zip at `<api>/downloads` (the file is in the api image, built from the same release), so after an update download it again from your own instance, replace the files in your folder and press reload on the extension card. A Chrome Web Store listing would update it automatically and is tracked in [issue 26](https://github.com/FindMalek/skiffr/issues/26).

### Known limits of the bundled setup

- the Caddy of the `domain` profile sets no request size limit and no security headers of its own (the apps send theirs, and the api sends HSTS on https)
- the release images are built without a public url: the pages read it at request time, but static output such as a sitemap or canonical link of the docs and site may say `localhost` until that is fixed
- the first admin is reset to the `.env` password on every api start

### Backup and restore

```bash
./skiffr backup                 # ./backups/skiffr-<time>.sql.gz
```

Keep `.env` with the dump: `CV_ENCRYPTION_KEY` and `BETTER_AUTH_SECRET` are not in it. To restore into a running stack:

```bash
docker compose stop api dashboard web
docker compose exec -T db psql -U skiffr -d postgres -c 'drop database skiffr' -c 'create database skiffr'
gunzip -c backups/skiffr-<time>.sql.gz | docker compose exec -T db psql -U skiffr -d skiffr
docker compose start api dashboard web
```

`docker compose down -v` deletes the volume, which is a full reset. Remove everything with it and delete the folder.

## Vercel

Deploy `web`, `dashboard` and `docs` as separate Vercel projects from the same repo.

1. import the repo and set the root directory to `apps/web`, then repeat for `apps/dashboard` and `apps/docs`
2. add the env keys to each project
3. host the `api` where bun or docker runs, and point `API_URL` and `API_PUBLIC_URL` at it

## Docker

To run the images without the compose file, every app has a `Dockerfile` in `apps/<app>/`. The build context is the repo root and turbo prunes the workspace to what the app needs:

```bash
docker build -f apps/web/Dockerfile -t skiffr-web .
docker build -f apps/dashboard/Dockerfile -t skiffr-dashboard .
docker build -f apps/api/Dockerfile -t skiffr-api .
docker build -f apps/docs/Dockerfile -t skiffr-docs .
```

Next apps are built with `output: "standalone"` and ship a healthcheck. Pass the env at run time.

## Dokploy

Create a project with a postgres database on the docker image `pgvector/pgvector:pg17` (answer embeddings need the `vector` extension), add one application per app with build type Dockerfile, path `apps/<app>/Dockerfile` and `.` as the context, set the env keys, and attach your domains. Use the api service's internal address for `API_URL`.

Do not swap the image of an existing database in place. The pgvector image uses a different libc than an alpine based postgres image, so text btree indexes silently break on the old data. Create a new postgres service with its own volume on `pgvector/pgvector:pg17` and restore with `pg_dump` / `pg_restore`, or at least run `REINDEX DATABASE` after any libc change.

`vector` is not a trusted extension, so `CREATE EXTENSION vector` needs a superuser. If the app's database user is not one, run it once as superuser, the migration's `IF NOT EXISTS` is then a no-op.

### Client address behind Traefik

The sign-in limits are per client address. Traefik replaces any `X-Forwarded-For` a client sends with the address it saw (unless you set `forwardedHeaders.trustedIPs` or `insecure` on the entrypoint, which you should not), so the api gets one value and the default `TRUSTED_PROXY_COUNT=1` is right. The dashboard passes the header on untouched. If a proxy of your own sits in front of Traefik and appends to the header, raise the count by one for each. If the api is reachable without any proxy, set `TRUSTED_PROXY_COUNT=0`, or a client could pick its own address. A request with no usable address shares one looser bucket and the api logs a warning once: check that with `select key from rate_limit` after a few sign-ins, you should see real addresses and not `192.0.2.1`.

## Self-hosting with GitHub Actions

`.github/workflows/deploy.yml` builds the four images for the project's own server on every green push to `main`, pushes them to `ghcr.io/<owner>/skiffr-<app>` (tags `main` and `sha-<commit>`, separate from the release tags in [releasing](/docs/releasing)), redeploys the Dokploy applications and then checks `/health` on the api and the other three sites. The api migrates the database when it starts. Nothing runs until the repo variable `DEPLOY_ENABLED` is `true`.

### One-time setup

1. point four DNS records at your server (a CNAME to its public name or an A record): the base domain for the landing page, and `dashboard.`, `api.` and `docs.` under it. Traefik issues the certificates through Let's Encrypt, so ports 80 and 443 must reach Dokploy
2. create a Dokploy API key (Settings, Profile, API keys)
3. run the bootstrap, first without `--apply` to read the plan:

```bash
DOKPLOY_URL=https://dokploy.example.com DOKPLOY_TOKEN=... \
  node scripts/dokploy-bootstrap.mjs --domain skiffr.example.com --env-file .env.production
# looks right? add --apply
```

It creates the `skiffr` project, a postgres on `pgvector/pgvector:pg17` (its user is the superuser the `vector` extension needs), the `skiffr-api`, `skiffr-web`, `skiffr-dashboard` and `skiffr-docs` applications, their domains and their env. It is safe to run again: existing things are kept and an env key that is already set in Dokploy is never overwritten. `BETTER_AUTH_SECRET`, the database password and, when `ADMIN_EMAIL` is given without a password, `ADMIN_PASSWORD` are generated and live in Dokploy only. The script prints key names, never values.

`--env-file` is optional and only these keys are read from it: `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `EXTENSION_ORIGINS`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_TOKEN`, the `S3_*` keys, the three Gmail keys, `AI_MODEL`, `GROQ_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and the [observability](/docs/observability) keys (`GLITCHTIP_DSN`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `AI_TRACE_CAPTURE_CONTENT`, `UMAMI_URL`, and per app `UMAMI_<APP>_WEBSITE_ID`, `GLITCHTIP_WEB_DSN`, `GLITCHTIP_DASHBOARD_DSN`). Anything left out stays unset and the api still boots, see [environment](/docs/environment).

4. set the GitHub repo settings below, then run the `deploy` workflow once from the Actions tab

| Where | Name | Value |
| --- | --- | --- |
| variable | `DEPLOY_ENABLED` | `true` |
| variable | `PRODUCTION_DOMAIN` | the base domain, for example `skiffr.example.com` |
| variable | `DOKPLOY_URL` | the public url of Dokploy |
| secret | `DOKPLOY_TOKEN` | the Dokploy API key |
| variable, optional | `TURBO_API`, `TURBO_TEAM` | a turbo remote cache for the image builds |
| secret, optional | `TURBO_TOKEN`, `GHCR_READ_TOKEN` | the cache token, and a `read:packages` token if the ghcr packages are private |

`DOKPLOY_URL`, `DOKPLOY_TOKEN` are the same settings the PR previews use.

Back up the database from Dokploy (Backups tab of the postgres service) to an S3 destination. The `backup` workflow only works against a database that is reachable from GitHub.

### Rollback

A deploy that dies in its first seconds keeps the old container (Dokploy services start first and roll back on failure). To go back to an older version set the previous `sha-` tag on the application in Dokploy, or run the workflow again on an older commit. A bad migration is not rolled back.
